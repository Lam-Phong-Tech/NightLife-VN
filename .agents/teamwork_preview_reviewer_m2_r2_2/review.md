## 2. Review Criteria Assessment

### Criteria 1: Deep Keyset Pagination
- **Requirement**: Confirm that querying pages past 60 items (e.g. page 4, 5, 6 with `limit = 20`) successfully returns subsequent pages without premature truncation or empty `data: []`.
- **Findings & Verification**:
  1. Previously, Prisma `findMany` queries fetched top 60 records starting from offset 0 without passing cursor conditions into the database queries (`where`). Consequently, when pagination reached page 4 (>60 items), in-memory filtering discarded all returned records because all 60 items were earlier than the cursor threshold, producing premature truncation (`data: []`, `hasMore: false`).
  2. The remediation incorporates database-level cursor conditions directly into `where.AND` for all 3 underlying Prisma models:
     - `Bill`: `submittedAt < cursorTime OR (submittedAt = cursorTime AND id < rawBillId)`
     - `CouponIssue`: `usedAt < cursorTime OR (usedAt = cursorTime AND id < rawCouponId)`
     - `Booking`: `scheduledAt < cursorTime OR (scheduledAt = cursorTime AND id < rawBookingId)`
  3. With database-level cursor filtering active, Prisma returns up to `limit * 3` items starting strictly **after** the cursor boundary. Deep pagination past 60 items (pages 4, 5, 6, 100+) continues to retrieve valid records until the dataset is exhausted.
  4. Unit test `applies database-level cursor filtering for deep pagination past 60 items` verifies this behavior against mock database queries and passes cleanly.

### Criteria 2: Timezone Range Edge Cases
- **Requirement**: Verify single-day filtering (`startDate = "2026-08-05"`, `endDate = "2026-08-05"`) captures events across the full 24 hours of Vietnam local time.
- **Findings & Verification**:
  1. Implemented helper `parseVietnamDateBoundary(dateStr: string, isEnd: boolean): Date` in `nightlife-data.service.ts`.
  2. Normalizes `YYYY-MM-DD` inputs to explicit `+07:00` offset:
     - `startDate = "2026-08-05"` -> `2026-08-05T00:00:00.000+07:00` (UTC `2026-08-04T17:00:00.000Z`).
     - `endDate = "2026-08-05"` -> `2026-08-05T23:59:59.999+07:00` (UTC `2026-08-05T16:59:59.999Z`).
  3. Also supports ISO midnight strings (`YYYY-MM-DDT00:00:00.000Z`) generated by standard client serializers, re-anchoring them to local Vietnam start-of-day and end-of-day bounds.
  4. Events recorded at early morning hours (e.g., 01:00 AM VN local time / 18:00 UTC previous day) or late night hours (23:59 PM VN local time / 16:59 UTC current day) are fully captured within the query range.
  5. Unit test `normalizes YYYY-MM-DD date range inputs to Asia/Ho_Chi_Minh (+07:00) day boundaries` verifies exact UTC timestamp calculations and passes cleanly.

## 4. Adversarial Stress-Test & Edge Case Analysis

1. **Heterogeneous Cursor Across Entity Types**:
   - *Scenario*: Cursor originates from a `bill:` entity, followed by pagination querying `Bill`, `CouponIssue`, and `Booking`.
   - *Stress Test*: When `rawCouponId` or `rawBookingId` is null, entity-specific cursor filters fallback to `usedAt < cursorTime` / `scheduledAt < cursorTime` for tied timestamps. The secondary in-memory filter `item.id < decodedCursor.id` acts as a tie-breaker.
   - *Result*: Correct items are fetched without missing ties or duplicating records.

2. **Malformed Date Strings**:
   - *Scenario*: Caller passes an unparseable string like `startDate = "invalid-date"`.
   - *Stress Test*: `parseVietnamDateBoundary` throws `BadRequestException('Invalid date format: ...')`.
   - *Result*: Fails safely with NestJS HTTP 400 Bad Request error.

3. **Limit Boundary Enforcement**:
   - *Scenario*: Caller requests `limit = 100` or `limit = -5`.
   - *Stress Test*: `Math.min(Math.max(dto.limit || 20, 1), 50)` constrains limit strictly between 1 and 50.
   - *Result*: Protects backend memory and database query load.
